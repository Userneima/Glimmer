# Agent 工作台设计

> 状态：第一阶段做成过桌面版右下角的 agent 浮窗，2026-10-28 从界面撤下（代码保留，见 `ai-handoff/CURRENT_STATE.md`）｜设计写于 2026-08-10
>
> 把 Glimmer 从"日记与知识管理应用"扩成"以 Agent 为主入口的日程与项目工作台"。本文只覆盖**第一阶段**：背景萃取与现状维护。后续阶段在文末列出，不在本文展开。

---

## 一、要解决的问题

使用者每天与 AI 产生的对话内容，已经超出人力总结的范围。实测：`~/.claude/projects/` 下 14 个项目、158 个会话、778 MB，时间跨度 2026-07-06 至 2026-08-09 共 27 天，**平均每天约 29 MB**。

这些内容里包含了真正在推进的事、被推翻的判断、遇到的障碍和做出的决定，但它们分散在按项目切分的会话文件里，没有横向视图，也没有随时间的沉淀。

同时，`docs/diary-writing-habits.md`（基于 103 篇既有日记的分析）指出：使用者的日记**本来就在承担工作台的角色**——流水账、任务捕捉、项目复盘、产品思考混在一起，"日记承担了过多角色"。本设计是把这个既成事实正式化。

---

## 二、目标与非目标

### 目标

1. 从既有 AI 对话中萃取出一份**真实且持续更新的背景与现状**。
2. 基于它自动产出日记，内容取自使用者自己说过的话，不编造。
3. 使用者纠正后，缺失的**背景**被补上（而不是新增一条规则）。
4. 手写日记功能完整保留，不受影响。

### 非目标（本阶段明确不做）

- 不做对话式任务管理（第二阶段）。
- 不做思想伙伴式的拔高讨论（第三阶段）。
- 不做面向他人的分发：不打包 Claude Code 二进制、不做安装引导、不做计费、不处理他人密钥。
- 不改动 Web 端。Web 端保持现状（手写 + 既有 DeepSeek 轻功能）。

---

## 三、核心判断

**系统的中心不是日记，也不是任务列表，而是一份持续维护的「背景 + 现状」。** 日记是它的人类可读切片，任务是它的执行面，对话是它的接口。

这个判断决定了后续三个阶段（任务规划、思想伙伴、忽略项提醒）都建立在同一份文件上，而不是各做各的。

配套的第二个判断：**不给 Agent 写死判据，给它背景。** 信息对一个了解使用者处境的人显不显眼，本来就是可判断的；把判据写死会限制它，也会让规则文件随时间膨胀。参考依据：Anthropic 官方在 2026 年 7 月公开表示 Claude Code 的系统提示词缩小了 80%，理由是"我们之前把 Claude 限制过头了"。

## 四、架构

### 4.1 运行位置

Agent 通过 **Tauri sidecar** 运行 Claude Agent SDK（Python 或 TypeScript），SDK 内部把 Claude Code 命令行作为子进程拉起。

- 仅桌面端。Web 端没有可运行 Agent 的进程。
- 因为只服务使用者本人，**直接依赖本机已安装的 Claude Code**，不打包 271 MB 二进制。
- 模型默认 `claude-opus-5`，通过 `ClaudeAgentOptions.model` 配置；`env` 可注入 `ANTHROPIC_BASE_URL` 以指向兼容端点。**换模型是改配置，不是改架构**，因此当前不为成本做任何取舍。

### 4.2 产物

工作目录是一个独立的 git 仓库（不在 Glimmer 源码库内），三类文件：

| 产物 | 路径 | 写入语义 |
|---|---|---|
| 背景 · 我 | `背景/我.md` | 低频更新。角色、能力边界、在追求什么、工作方式、自己会处理不用 Agent 管的事 |
| 背景 · 长期 | `背景/长期.md` | 低频更新。长期规划、目标与时间线，以及现实约束（时间分配、交付节点、精力与预算边界） |
| 现状 | `现状/<项目>.md` | 每日**覆写** |
| 日记 | `日记/YYYY-MM-DD.md` | 每日**新建** |

**现状为什么是覆写而不是追加**：追加会让它退化成第二份日记。「当前状态」这一语义要求随时可读、不需翻阅。历史不丢——目录用 git 管理，每天一次提交，`git log` 即演进过程。

**没有规则文件。** 早期设计中的 `判断/规则.md` 已删除，其职责由背景文件承担。

### 4.3 数据流

```
~/.claude/projects/*/*.jsonl   ─┐
  （仅取 type == "user" 的记录，   │
    按 timestamp 取当天新增）      │
                                  ├─→ [ Agent ] ─→ 更新 现状/*.md
昨天的 现状/*.md                ─┤              ─→ 新建 日记/YYYY-MM-DD.md
背景/我.md、背景/长期.md        ─┤              ─→ git commit
Glimmer 当天碎片与任务完成情况   ─┘
```

**只读 `type: "user"` 的记录。** AI 的回复里是它自己的推理过程；把它总结进日记，得到的是"AI 今天做了什么"，而不是"我今天想了什么"。使用者的日记是个人工作记忆，原始来源只在自己说过的话里。会话文件中两类记录是分开的，实现上直接可做。

**增量而非全量。** 778 MB 每天全读既不可行也无必要——现状文件本身就是此前所有日期的压缩结果。这对应"结构化笔记：把状态外置到上下文之外的文件"。

### 4.4 Agent 的自由度边界

**给什么**：背景文件、当天原始对话、现状文件、文件读写、Bash。

**不给什么**：判据、模板、必须有的步骤顺序、长度要求。

**三条硬底线**（唯一的约束）：

1. 忠于材料，不写入材料里没有的内容。
2. 不确定就标出来。一句通顺但没依据的话，比一句"此处不确定"糟糕得多。
3. 每一条都可追回来源（项目、会话、原话）。

### 4.5 纠正循环

日记与现状中的每一条都带来源标记。使用者划掉某条时，Agent 追问一次：**"我缺了哪一块背景，才会认为这条值得记？"**

- 答案补进 `背景/*.md`。
- **不产出新规则。**
- 沉淀新背景时，同时检查是否有旧背景已被取代或过期，**有增必有删**。

**这一条的验收标准是：三个月后背景文件更短更准，而不是更长。**

## 六、失败与错误处理

| 情况 | 处理 |
|---|---|
| 本机未安装 Claude Code | 桌面端启动时检测，给出明确提示，不静默失败 |
| 某天没有任何 AI 对话 | 正常产出，日记只含 Glimmer 侧碎片与任务；不因空输入报错 |
| Agent 中途失败 | **不写半份文件**。现状与日记先写临时文件，成功后原子替换；失败则保留昨天的现状不变，并记录失败原因 |
| 单个会话文件损坏或解析失败 | 跳过该文件并在日记末尾标注"某会话未能读取"，不中断整体运行 |
| 使用者当天电脑未开机 | 下次运行时按时间范围补跑，不假设每天连续 |
| 产出内容明显跑偏 | 目录是 git 仓库，`git revert` 即可回退；**不做自动删除** |

一条与现有 FluentFlow 教训一致的原则：**检查只报告，不销毁**。不合格的产物改名保留，不删除。

## 七、验收标准

不以"跑起来了"为准，以下面三条为准：

1. **连续一周的日记，读完不觉得需要补充**——说明没漏。
2. **里面没有不关心的内容**——说明筛选准确。
3. **随机抽一条，能追回原始对话**——说明可核。

背景萃取阶段另有一条：**使用者读背景初稿时，修改量应低于三成**。高于三成说明萃取深度不够，需要按知识萃取方法回炉（打断模型、逼它重读原始记录）。

## 八、实施顺序

**第 0 步（一次性，最关键）**：从 778 MB 对话中萃取背景初稿。方法遵循知识萃取五步——原始数据全给不预筛、用最强模型、不允许写关键词脚本做选择性读取、萃取到一半打断并逼其重读原始记录、与使用者来回校验。产出 `背景/我.md` 与 `背景/长期.md` 初稿，使用者修改后定稿。

**第 1 步**：每日运行。读昨天现状 + 当天使用者消息 → 更新现状、写日记 → git 提交。

**第 2 步**：纠正循环接入 Glimmer 界面。

第 0 步的质量决定后面所有判断的质量，不能跳过或简化。

## 十、已知风险与未决问题

**风险一：背景失真。** 自由度的前提是背景真实且完整。背景若空泛或经过美化，Agent 会**自信地跑偏**，且比规则跑偏更难发现——因为它的推理看起来是合理的。背景文件的质量直接决定系统上限，是唯一不能糊弄的部分。

**风险二：有些判断推不出来。** 部分价值判断无法从任何背景推导（例如"同学轮流讲自己项目不算废话"）。这类仍需显式写入，但应写成**关于使用者的事实**，而非给 Agent 的禁令。

**未决一**：现状文件按项目切分是否够用。跨项目的联系（同一个想法在两个项目里出现）目前没有承载位置，可能需要第三类文件，待第一周实际产出后判断。

**未决二**：每日运行的触发方式。定时任务、开机触发、还是打开 Glimmer 时触发，取决于实际使用节奏，第一步先用手动触发验证内容质量。

**未决三**：Glimmer 侧展示这些 markdown 的入口形态，待第一阶段内容稳定后再设计，避免过早定 UI。

**未决四**：工作目录（背景、现状、日记所在的 git 仓库）放在哪。候选是 Tauri app data 目录下，或使用者自选的一个普通目录。前者随应用管理、后者便于自己用编辑器和 git 直接操作。倾向后者，但第一步先手动指定一个路径验证内容，不急着定。
