# PRODUCT_BRIEF

它只回答一个问题：**Glimmer 这个产品到底要解决什么问题，以及为什么某些体验标准不能退让。**

## 产品一句话定义
Glimmer 是一个本地优先的日记与轻知识管理 Web 应用，核心任务不是堆功能，而是让用户在“写下内容、稍后整理、需要时导出或同步”之间自然切换，不被工具本身打断。

## 产品分工（2026-10-28 定）
日记由人来写。Glimmer 的界面是一块看板：写日记、看日记、找日记、直接改正文都在这里。Claude 负责围绕日记的复杂或低频操作，比如整理文件夹、成批导入导出、调整模板、按问题查找和汇总过去的日记；它不替人写日记，也不改写人写的正文。之前工作台让 agent 每天自动写日记，用下来不如自己写，所以 agent 写的内容不再进日记列表。

- Claude 读日记不需要改产品：桌面版的日记全部存在 `~/Library/Application Support/com.yuchao.glimmer/glimmer-store.json`（`diaries-<用户 id>` 键，正文是 HTML），Claude 只读这个文件。怎么读、怎么组织、什么时候开口，写成一个 skill，按使用者的反馈和模型的变化随时改，不做进 Glimmer 的代码。
- Claude 要改 Glimmer 的数据时，不直接写这个文件，也不直接写云端：它往桌面版的收件箱里放一张改动单，由 Glimmer 核对后用界面同一条路径去改，本机、云端、其他设备都能看到，改完能撤回（2026-11-03 起，做法见 `CURRENT_STATE.md`「Claude 改文档」）。能改哪几篇有一张允许清单，现在只有「长期任务」；他写的日记正文仍然只读。要放开新的一类（整理文件夹、加标签等），一项一项加，每加一项先问使用者。
- 新功能先问一句：这是每天写和看时要用的吗？是就做进界面；不是就交给 Claude，界面上不加入口。
- Claude 可以从日记里积累对使用者的了解，也可以推测使用者没写明的想法和目标，前提是使用者知道：每次往档案里加东西或做出推测，都在当次对话里告诉使用者加了什么、依据是哪几篇日记，推测和使用者确认过的事实分开标。档案只有一份，放在使用者自己的个人资料仓库里（不在本仓库），Glimmer 和 Claude 都不另建副本。

## 核心问题
这个产品要解决的不是“用户没有地方记东西”，而是以下几类更具体的问题：

- 纯文本笔记太弱，用户写日记、计划、表格整理时很快撞到格式边界。
- 只强调编辑器的工具往往忽视组织与后续回看，内容写下去后不容易按文件夹、搜索、任务重新找到。
- 很多工具把同步、AI、复杂设置放在主流程前面，导致写作本身反而变重。
- 个人内容一旦强依赖云端或单一平台，保存感和导出能力会变差。

Glimmer 的答案是：先把“写作和保存”做稳，再把组织、导出、同步、AI 放成增强层。

## 目标用户与典型使用方式
目标用户不是企业协作团队，而是想要一个安静、低负担、可长期积累的个人写作空间的人。典型使用方式包括：

- 按天写日记，同时记录当天计划、待办、情绪、事件。
- 用文件夹、搜索和任务线索回看过去内容。
- 在正文里混合使用标题、任务列表、表格、图片。
- 平时主要在本机使用，必要时再通过登录实现跨设备同步。
- 写完后再决定是否用 AI 做分析、是否把片段提炼成长期想法。

## 当前产品成立的关键体验标准
- 写作必须顺手。打开就是内容，不应该先处理登录、同步、复杂配置。
- 保存必须可信。本地内容不能因为网络、云端、配置错误而丢失或被空数据覆盖。
- 组织必须轻量。文件夹、搜索、任务和长期想法都应该帮助“回看和整理”，而不是变成新的操作负担。
- 导出必须可用。用户需要能把积累带走。
- 增强能力不能反客为主。云同步、AI、长期想法都应建立在主写作流稳定的前提上。

## 明确不追求什么
- 不追求团队文档协作，不是知识库后台，也不是项目管理平台。
- 不追求把所有可能的 AI 功能塞进主界面。
- 不追求为了“看起来先进”而牺牲写作流和保存可靠性。
- 不追求把每个侧栏、弹窗、抽屉做成独立视觉系统。界面要服从主工作区，而不是抢戏。
